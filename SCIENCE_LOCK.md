# Scientific Lock

## Purpose

This document defines the scientific boundary between the frozen osteosarcoma study and the reusable Molecular Transport Audit software project.

The software project may generalize, refactor, test, document, orchestrate, and expose existing computational procedures.

It must not retroactively change the scientific design of the source study.

This document should be reviewed before any proposed analysis extension is implemented.

---

## 1. Source-of-truth principle

The original osteosarcoma repository and its finalized analysis outputs remain the scientific source of truth for the first study.

The reusable implementation must initially be treated as a refactor of frozen computational logic rather than as an opportunity to optimize scientific results.

If the reusable implementation and a locked source result disagree, the discrepancy must be investigated before the reusable result can replace or reinterpret the reference result.

---

## 2. Frozen scientific objects

The following scientific objects from the osteosarcoma study must not be redefined by this software project:

- frozen molecular program membership;
- frozen molecular program weights;
- frozen score directions;
- discovery-versus-validation roles of cohorts;
- primary endpoint definitions;
- primary human outcome tests;
- inferential-family definitions;
- multiplicity-control families;
- outcome-blind assay rules;
- interpretation of assay-sensitive analyses;
- final evidence hierarchy.

In particular, the programs M34, M11, M24, and M40 must not be modified to improve downstream validation results.

---

## 3. Prohibited changes

The Paper 1 software extension MUST NOT:

- select new genes using target-cohort outcomes;
- remove genes because they weaken target-cohort results;
- reverse frozen score directions after viewing target outcomes;
- re-weight frozen programs using target outcomes;
- introduce new clinical endpoints to obtain stronger significance;
- replace a locked primary analysis with a more favorable sensitivity analysis;
- combine previously separate multiplicity families post hoc;
- change statistical thresholds solely because existing conclusions are inconvenient;
- reinterpret assay-sensitive behavior as biological reversal without independent evidence;
- add multimodal representation learning;
- add methylation modeling;
- add ATAC-seq integration;
- add proteomics integration;
- add CNV integration;
- add spatial multi-omics learning;
- introduce a new cross-modal neural network;
- introduce a new disease-discovery project as part of the osteosarcoma scientific result.

These topics are outside the scientific scope of Paper 1 and are reserved for future work where appropriate.

---

## 4. Permitted software work

The project MAY:

- refactor existing computational procedures into reusable functions;
- replace hard-coded paths with explicit inputs and configuration files;
- standardize data schemas;
- create reusable input validation;
- create reusable reporting;
- expose frozen analyses through a Python API;
- orchestrate analyses with Nextflow;
- expose the workflow through FastAPI;
- build a React interface;
- containerize execution;
- create local and SLURM execution profiles;
- add documentation;
- add unit tests;
- add integration tests;
- add scientific regression tests;
- create example datasets;
- create provenance manifests;
- create deterministic resampling schedules where compatible with the frozen analysis;
- improve runtime or memory efficiency without changing statistical definitions;
- add adapters for established bioinformatics tools when their scientific role already exists in the framework.

---

## 5. Regression-testing requirement

A reusable implementation is not considered validated merely because it produces plausible output.

For each migrated scientific component, the new implementation must be tested against a locked reference artifact from the source study.

Each reference artifact must identify, where available:

- source repository;
- source script;
- source script version;
- source Git commit;
- input dataset or input manifest;
- input hashes;
- output file;
- output hash;
- random seed;
- software environment;
- scientific status.

Reference artifacts generated by superseded or known-buggy script versions must not be used as authoritative regression targets.

---

## 6. Numerical reproducibility policy

Different numerical procedures require different regression strategies.

A single global numerical tolerance must not be used for all analyses.

### 6.1 Deterministic calculations

Deterministic scalar calculations should use tight numerical tolerances.

Tolerance must reflect expected floating-point behavior rather than convenience.

### 6.2 Cross-language numerical calculations

Analyses involving Python, R, BLAS, LAPACK, or platform-dependent numerical libraries may exhibit small floating-point differences.

Metric-specific absolute and relative tolerances will be stored in a version-controlled regression configuration.

A tolerance must not be widened solely to make a failing regression test pass.

### 6.3 Bootstrap and permutation analyses

Where original resampling assignments are available, the reusable implementation should reuse the same assignments.

Where they are not available:

- the original randomization procedure must be documented as closely as possible;
- the RNG implementation and seed must be recorded;
- the regression target must distinguish expected Monte Carlo variation from implementation errors;
- inferential classification must not change silently.

Whenever practical, future reusable runs should persist resampling schedules so the same randomization can be replayed across environments.

### 6.4 Latent-factor analyses

Latent representations may be invariant to:

- factor sign;
- factor ordering;
- equivalent rotations or representations permitted by the model.

Regression tests must therefore compare scientifically invariant quantities rather than requiring arbitrary factor labels or signs to match exactly.

### 6.5 Scientific conclusions

Regardless of small numerical drift, a refactor must not silently change the scientific classification of a frozen result.

Any change affecting:

- significance status;
- direction;
- evidence class;
- module classification;
- primary interpretation

requires explicit investigation and documentation.

---

## 7. Randomization policy

Randomness must be explicit.

New reusable components should avoid hidden global RNG state.

Each stochastic run should record:

- random seed;
- RNG implementation where relevant;
- number of permutations or resamples;
- sampling strategy;
- hashes of persisted resampling schedules where used.

R and Python must not be assumed to produce identical random sequences from the same numeric seed.

When cross-language identity is required, explicit resampling assignments should be generated and exchanged as data rather than relying on language-specific RNG equivalence.

---

## 8. Provenance requirement

Every completed software run should eventually emit a machine-readable manifest containing at least:

- software version;
- Git commit;
- configuration hash;
- input hashes;
- frozen-program hash;
- ortholog-mapping hash where applicable;
- randomization metadata;
- executed workflow components;
- container or environment information;
- output hashes.

Live external resources must not silently alter a reproducibility run.

For example, updated online ortholog mappings must be materialized, versioned, hashed, and frozen before analysis.

---

## 9. Separation from future multimodal work

The current project audits transport of molecular programs.

A future multimodal project may address questions such as:

- shared versus modality-specific biological states;
- RNA-to-ATAC relationships;
- DNA methylation;
- protein abundance;
- CNV;
- spatial organization;
- multimodal latent representations;
- cross-species multimodal alignment;
- new machine-learning objectives;
- simulations with known ground truth;
- multi-disease benchmarking.

Those are distinct scientific contributions and must not be absorbed incrementally into this repository simply because the implementation makes them technically possible.

---

## 10. Change-control rule

A proposed change that alters scientific scope must be classified before implementation.

The question is:

> Does this change improve software implementation of an already-defined analysis, or does it introduce a new scientific question?

If it introduces a new scientific question, it must not be added automatically.

It requires an explicit decision about whether it belongs to:

- the current paper;
- a sensitivity analysis;
- a separate validation study;
- or a future paper.
